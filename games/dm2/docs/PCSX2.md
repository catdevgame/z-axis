## The hook

- `scePadRead` is `0x001D9358`; its only caller is `jal` at `0x00113108` in `func_00112D98`
  (per-port pad state machine), buffer `a2 = 0x00260494` (32 bytes, same layout as AI:
  `[2..3]` buttons active-low, `[4..7]` RX RY LX LY, `[8..19]` pressure). The pad is a
  DualShock 2 in pressure mode (id 0x79). That call becomes `jal pad_hook` (0x000F8000); same
  mailbox as AI at `0x000F7000` (`+0x04` buttons active-high, `+0x06` stick override,
  `+0x08` sticks, `+0x0C` polls, `+0x14` VBlank count at the first poll).
- DM2 has no VBlank callback (its frame loop blocks in `sceGsSyncV`), so the hook also
  registers an INTC 2 handler that counts VBlanks into `MAILBOX+0x18` (installed from the
  graphics-init call `jal 0x00100388` at `0x00100528`, fallback on the first poll; `+0x1C`
  = installed). All tool timing uses that counter. Lines are `patch=2` so the init call site
  is patched before the game reaches it.
- Schedule (as BMX XXX's hook, with sticks): 16-byte entries at `0x000D0000` (u32 key, u32
  buttons | flags << 16, bit 16 = set the sticks, u32 RX RY LX LY bytes), count at
  `MAILBOX+0x30`, next at `+0x34`, the held entry at `+0x38`/`+0x3C`. The key is a level frame
  (`0x25BCC4`) or, with bit 31, a VBlank count (the front end). At every poll each due entry is
  taken and the last one held, OR'ed with the mailbox's buttons; so input lands on exactly the
  frames (or vsyncs) it says, with no PINE latency. `dm2pcsx2.py schedule FILE` loads one
  (`KEY BUTTONS [LX LY]` lines, `<n>v` for a VBlank count), `waitframe N` waits on the level frame.
  An empty schedule changes nothing: run 1's seen log loaded as a VBlank schedule replays run 1
  to the same seen log and the same 6 value lines (posbits included). The RAM outside the hook's
  area differs only at the hook's own addresses, the kernel's interrupt frame and a cycle-count
  stamp (`0x2606C8`, the hook's extra cycles).
- PINE-timed input lands +-1 vsync (the game's read can come before or after a PINE write in
  the same vsync) and a `checkpoint` blocks 30 to 120 vsyncs: replays that must be exact use the
  schedule, and PINE only reads.
- Seen log: ring at `0x000E0000` (4096 x 16 bytes, count at `MAILBOX+0x24`): every read whose
  final buttons/left stick changed, with its VBlank count, level frame and poll count.
  `dm2pcsx2.py seenlog FILE` saves it; that is the exact input the game saw, used for native
  replays.
- `0x00096000-0x000FFFFF` stays zero in boot, menus, loading and in level, apart from the hook.

## dm2pcsx2.py

Same verbs as AI's pcsx2pad.py (`press hold down up stick release wait waitsec waitpolls
waitmem waitval pressuntil script run peek peekf poke dump savestate loadstate checkpoint
status frame`), plus `waitvsync N`, `state` (DM2 anchors and rider), `seenlog FILE`,
`padscript SEENLOG [DELAY]`, and `shot FILE` (the emulated frame from a savestate
thumbnail, 640x480). Use `shot`, not `screenshot`: when the PCSX2 window is not visible the
window capture is stale. `script` accepts the native syntax including `<t>v` and `LX=`.

## Logic check (`dm2logic.py`)

`refvalues` writes `scripts/dm2-ref-run1-values.txt` from the checkpoint RAM images
(`recomp/dumps/ref`, not committed); `run NAME` runs the native runner with the padscript,
`ZX_PAD_SCRIPT_CLOCK=vsync`, `ZX_DUMP_WHEN` at the checkpoints' script times, scratch
HOME / app support / memory cards under `$ZAXIS_SCRATCH/dm2logic` (DM2_SCRATCH), `ZX_GS_NULL=1` by default, and
stops when all six dumps exist; `compare NAME` prints the table.

Run 1: all 6 checkpoints match within 0.01 (about 95 s wall). The SYNC anchors move the native clock,
because native loads are faster. The level frame counter reads one more natively at every in-level
checkpoint: a sampling difference (the PCSX2 savestate lands while the EE is still in the frame,
after the rider physics, before the counter increment), allowed by `DM2LOGIC_FRAME_SKEW=1`. The rider's
position is not bit-exact from the level start on: run 1's presses are vsync-timed and its dumps are
taken at script times, a frame late natively, so the difference grows to about 0.01 units.

Run 2 (`dm2logic.py --run 2`): the native script anchors every level input on the level frame
(bmxlogic's method, LX/LY included) and dumps each level checkpoint at the VBlank where the
counter reaches its frame (a PCSX2 savestate at counter f is the native VBlank at counter f: a
dump at f+1 is a frame of motion ahead). A pass is 21/21 MATCH, with the rider's position bit-exact
at every checkpoint. `DM2LOGIC_INPUT_DELAY=N` makes the presses N vsyncs late (run 2's level inputs: N
level frames), a negative test: the check must fail. `--ref DIR` checks a re-recorded reference in one folder
(DIR/seen.txt, commands.txt, values.txt, ram/) as run 1 is, or with `--by-frame` as run 2 is.
